# M63: 현대차 내비로 전 구간 측정 · 날짜별 순서 최적화 (2026-11-13)

차량에서는 현대차 내비가 시간·거리·순서의 기준이다. 휴대폰의 카카오 값은 일정을 짤 때 쓰는 예상값이고, 차량에서 내비가 잰 구간은 그 값을 대신한다.

시험 환경은 Pleos Connect Emulator(내비 위치 성남 수정구 시흥동, 금요일 17:55~18:25)와 서명 release 0.6.0, 배포 서버로 연동한 샘플 여행 '강릉 3박 4일'이다. 방법의 근거(경유지별 남은 값의 차이 = 구간 값)는 `docs/evidence/navi-waypoints`에 있다.

## 확인한 값

- 전 구간 측정: 13구간, 경로 2번, 약 26~30초. 2일차 구간 3·7·12·6·9분(휴대폰 계획값 5·10·15·10·15분).
- 1일차 순서: 뒤섞은 순서 199분 → 내비 기준 가장 빠른 순서 188분(11분 단축). 제안된 순서는 샘플의 원래 순서와 같다.
- 시험: Kotlin 208(`NaviPlanTest` 15건), 차량 E2E 16항목, 실제 연동 15항목(서명 release ↔ 배포 서버).

## 만들면서 알게 된 것

- 경로를 걸면 내비 앱이 앞에 나오고, 뒤에 있는 앱은 약 10초 뒤 시스템이 정지시킨다(`isFrozen=true`). 측정 동안만 짧은 포그라운드 서비스(`MeasureService`)로 붙잡는다.
- 내비가 돌려주는 경유지에는 좌표가 없다(0, 0). 보낸 이름과 순서로 같은 경유지인지 확인한다.
- 경로가 없을 때 취소를 보내면 내비가 그 뒤 모든 취소를 무시한다(내비 앱을 다시 시작해야 풀림). 목적지가 있을 때만 취소한다.
- 측정이 끝나면 앱이 앞으로 돌아오기를 요청하지만 시스템이 막는 경우가 있다(백그라운드 화면 전환 제한). 그때는 사용자가 떠날지도로 돌아오면 결과가 떠 있다.

## 확인하지 못한 것

- 실차: 내비가 받는 경유지 수(에뮬레이터 9곳. 덜 받으면 받은 수로 다시 나누도록 했지만 그 경로는 단위 시험뿐), 경로 시작 음성, 포그라운드 서비스에 대한 심사 기준.
- 차량 E2E 16항목과 실제 연동 15항목은 취소 방식을 고치기 전 빌드로 돌렸다(그 뒤 바뀐 것은 내비 취소·확인 문구·주행 시 중단뿐이고, 측정 → 경로 없음 → 안내 시작은 최종 빌드로 다시 확인).
- 방문을 시작한 날의 남은 장소 순서 최적화(지금은 아직 시작하지 않은 날만).
